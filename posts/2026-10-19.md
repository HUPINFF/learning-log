### sqlalchemy

sqlalchemy这个是Python和数据库之间的一层**翻译** + **管理工具** 。分清它在整个栈中的位置：
Python代码 
-> sqlalchemy(翻译Python对象/语句-> SQL；管理:连接池，事务，对象状态)
-> pymysql  驱动：把SQL字符串真正通过网络发给MySQL   
-> MySQL 服务器

注意：sqlalchemy 自己不会连接数据库，真正和数据库说话的是pymysql,sqlalchemy在它上一层

sqlalchemy有两个版本 Core和ORM

# ① 原生 SQL（text）—— Core 里的逃生口
conn.execute(text("SELECT count(*) FROM jobs")).scalar()

# ② Core 表达式语言 —— 用 Python 对象拼 SQL，但不涉及"实体类"
jobs = Table("jobs", metadata, Column("job_id", Integer, primary_key=True), ...)
conn.execute(select(func.count()).select_from(jobs)).scalar()

# ③ ORM —— 用模型类拼 SQL，结果回对象
session.scalar(select(func.count()).select_from(Job))


- Core管"咋和数据库说话"； ORM管的是"数据库的行怎么变成Python对象"。

- 它们的差别：
对于Core :表是Table对象/字符串表名，一行得到的是Row; 谁执行：with engine.connect()
事务：with engine.begin(): ; 改数据时要手动写UPDATE/INSERT来和数据库通信，没用状态跟踪认不出同一个对象
对于ORM: 表就是一个Python类(class Job(Base)) 一行就是一个Job实例，属性就是列； 谁执行：Session  ; 事务: with Session(engine): ; 改对象属性，commit()自动转UPDATE； 外键job.company.name ; 有状态跟踪


使用场景：
1. 批量数据灌入数据库时              用Core
2. 聚合报表(GROUP BY ,COUNT,AVG)时  用Core ,结果就是数字，不用对象形式
3. 查数据记录返回给前端              用ORM
4. 需要改数据                       用ORM (省得自己写UPDATE)
5. 复杂SQL语句(多表子查询)           用sql/Core，写起来简单


### SQL语句的复习

主要就是回顾回顾 GROUP BY:分组查询，相同值的分为一组，展示为一列
ORDER BY 对结果排序
LIMIT 截断， LIMIT XX OFFSET XX可以进行分页操作


### ORM 查询的写法骨架

看着写法很多，其实都是同一个骨架，只是换零件：

```
session.<终止方法>( select(<选什么>) .<子句①>() .<子句②>() ... )
```

**第一段：select() 里放什么 —— 决定 SELECT 列表**

| 写法 | 生成的 SQL | 拿回什么 |
|---|---|---|
| `select(Job)` | `SELECT jobs.* FROM jobs` | 整个 Job 对象 |
| `select(Job.job_id, Job.title)` | `SELECT jobs.job_id, jobs.title` | 元组 |
| `select(func.count())` | `SELECT count(*)` | 一个数字 |

**第二段：链式方法 —— 一个方法对应一个 SQL 子句**

| ORM 方法 | SQL 子句 |
|---|---|
| `.where(...)` | WHERE |
| `.join(...)` | JOIN |
| `.group_by(...)` | GROUP BY |
| `.having(...)` | HAVING |
| `.order_by(...)` | ORDER BY |
| `.limit(n)` / `.offset(n)` | LIMIT / OFFSET |
| `.options(...)` | **不是 SQL**，只是 ORM 的加载策略 |

方法按需要链，不用全写。链的顺序语义上可以换（每次都返回新对象），但按 SQL 子句顺序写才看得懂。

**第三段：终止方法 —— 决定拿回什么形状**

| 终止 | 返回 | 场景 |
|---|---|---|
| `session.scalar(stmt)` | 第一行第一列的值 / None | COUNT、AVG 这种一个数 |
| `session.scalars(stmt)` | ScalarResult，`.all()` 得列表 | 一串实体（Job 对象） |
| `session.execute(stmt)` | Result，每行是 Row | 选了多列、或跑 Core |

`scalar` 和 `scalars` 差一个 s，这里不能混。

**第四段：入口（真正的"不同写法"）**

- `session.get(Job, 1)` —— 按主键查一条，不用写 select/where
- `session.execute(text("..."))` —— 原生 SQL

是 4 个独立的选择组合起来：入口 × select 里选什么 × 子句 × 终止方法。


### N+1 查询问题

`select(Job)` 只查了 jobs 表，companies 的数据不在内存里。
每访问一次 `j.company`，Session 发现这个外键没加载过，就单独补一条：

```sql
SELECT company_id, name FROM companies WHERE company_id = %s
```

查 20 个岗位 → 1 条查 jobs + 20 条查 companies = **21 条**。
本来 1 条 JOIN 能解决。1000 行就是 1001 次往返。
**不报错、不警告，只是慢** —— ORM 项目最常见的性能事故。

解决：`select(Job).options(joinedload(Job.company))`，生成一条带 LEFT OUTER JOIN 的 SQL。

观察手段：`create_engine(url, echo=True)`，把 ORM 实际发出的 SQL 打出来。

### session.get() 的三种结果

```python
session.get(Job, 1)          # -> Job 对象
session.get(Job, 999)        # -> None，不抛异常
session.get(Job, "abc")      # -> None（不是报错）
```

| 输入 | 返回 | FastAPI 里对应 |
|---|---|---|
| 存在的 id | Job 对象 | 200 |
| 不存在的 id | None | 404 —— **必须自己判空**，ORM 不会抛异常 |
| 非数字字符串 | None | 422 是 FastAPI 给的，不是 ORM 给的 |

忘了判空直接 `job.title` → `AttributeError` → 接口 500。

**类型校验发生在哪一层：**

| 层 | 管不管类型 |
|---|---|
| ORM / SQLAlchemy | 不管，`get(Job, "abc")` 照样发给数据库 |
| MySQL | 隐式转换兜底：`'abc'` 转成 `0`，查不到，**不报错** |
| FastAPI + Pydantic | 这里才拦：`job_id: int` 的请求在进函数之前就 422 |

跟 `SELECT a AND b` 里中文字符串转 0、`region_main = '广东'` 返回 0 行，是同一个根子：
**MySQL 的隐式类型转换会静默吞掉错误**，ORM 这一层也不会帮你挡。


### stats 接口的 ORM 写法

**③ 学历分布**

```python
stmt = (
    select(Job.edu_required, func.count().label("n"))
    .group_by(Job.edu_required)
    .order_by(func.count().desc())
)
for row in session.execute(stmt):
    print(row.edu_required, row.n)
```

**④ 地区分布**

```python
stmt = (
    select(Job.region_main, func.count().label("n"))
    .group_by(Job.region_main)
    .order_by(func.count().desc())
    .limit(10)
)
for row in session.execute(stmt):
    print(row.region_main, row.n)
```

③④ 都用 `session.execute()` 而不是 `session.scalars()`——选的是**两列**（分组键 + 计数），不是实体对象。`row.edu_required` / `row.n` 是 `Row` 的列名访问。

**⑤ 薪资分档 —— `case()`**

```python
from sqlalchemy import case

bucket = case(
    (Job.salary_max.is_(None), 0),
    (Job.salary_max < 10000, 1),
    (Job.salary_max < 20000, 2),
    (Job.salary_max < 30000, 3),
    (Job.salary_max < 50000, 4),
    else_=5,
).label("bucket")

band = case(
    (Job.salary_max.is_(None), "未标注"),
    (Job.salary_max < 10000, "<10k"),
    (Job.salary_max < 20000, "10k-20k"),
    (Job.salary_max < 30000, "20k-30k"),
    (Job.salary_max < 50000, "30k-50k"),
    else_=">=50k",
).label("band")

mid = (Job.salary_min + Job.salary_max) / 2

stmt = (
    select(bucket, band, func.count().label("n"), func.round(func.avg(mid)).label("avg_mid"))
    .group_by(bucket, band)
    .order_by(bucket)
)
for row in session.execute(stmt):
    print(row.bucket, row.band, row.n, row.avg_mid)
```

`case()` 的语法和 SQL 不一样，是**元组列表**：`(条件, 值)`，最后一个 `else_=`。
对照 SQL 的 `CASE WHEN ... THEN ... ELSE ... END`。

三个容易写错的点：

- `Job.salary_max.is_(None)` 是 `IS NULL`。**不能写 `== None`**——那会生成 `= NULL`，而 `NULL = NULL` 结果是 NULL，永远不成立。
- `func.count().label("n")` 起别名，后面 `row.n` 才拿得到。
- `group_by(bucket, band)` 传的是带 `.label()` 的 `case` 表达式本身，SQLAlchemy 会把整段 CASE 塞进 `GROUP BY`，结果和 SQL 里写别名等价。
