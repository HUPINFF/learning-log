#  第八天  async def vs def：我的代码到底在谁手里跑

##  今天学了什么

1. `async def` 和 `def` 接口跑在不同地方（事件循环 / 线程池）
2. 线程不是我开的，是 FastAPI 的依赖库开的
3. GIL 释放帮的是别的线程，不让卡住的请求变快
4. 线程 vs 协程：区别是「谁有权切换」和「切换多贵」
5. 线程池里没有事件循环，所以不能 `await`
---



### Python 的 线程概念 
Python 本身就是单线程的，但是能开多个线程，但是不会并行执行，多个线程之间是并发的，
Python分为主线程(事件循环:异步操作)和 worker线程(只有40个)
所以Python 中实现并发并不只有异步操作能实现，Python的多线程之间也能实现并发，但并发数量有限

### FastAPI 只做一次判断

它只看函数的形状，**不进函数体分析**：

```python
if inspect.iscoroutinefunction(endpoint):
    await endpoint(...)                  # async def → 主线程的事件循环
else:
    await run_in_threadpool(endpoint)    # def → 丢进线程池
```

只对 **FastAPI 直接调用的那一个函数**（接口本身、每个依赖）生效。再往下它看不见。

| 谁 | 在哪 |
|---|---|
| `async def` 接口 / 依赖 | 主线程（事件循环） |
| `def` 接口 / 依赖 / `get_db` | worker 线程（线程池） |
| 它们内部调用的所有普通函数 | **跟着调用者走**，不是"归主线程" |

`def` 里的 `session.scalars()`、pymysql 的 socket 读写，全在 worker 线程里。

### 线程不是我开的

`main.py` 里没有一个 `threading`，线程仍然存在：

```
uvicorn → starlette → fastapi/routing.py: run_in_threadpool
        → anyio.to_thread.run_sync
        → anyio 的 WorkerThread(Thread)   ← 真正 new Thread 的地方
```

一眼验证：

```python
@app.get("/who")
def who():
    return {"thread": threading.current_thread().name}   # AnyIO worker thread

@app.get("/who-async")
async def who_async():
    return {"thread": threading.current_thread().name}   # MainThread
```

### 40 个线程是硬顶

anyio 默认限额 40。第 41 个请求**不是慢，是没线程可用**。

| 同时请求 | `def` | `async def` |
|---|---|---|
| 40 | 都跑 | 都跑 |
| 41 | 第 41 个排队等线程 | 都跑 |
| 1000 | 960 个干等 | 都跑 |

**并发上限 = 线程数，不是 CPU 忙不忙。** 一个慢接口（LLM 30 秒）占满 40 个线程，快接口全跟着排队——线程池最典型的线上事故。

### GIL 释放帮的不是你

```python
def endpoint():
    a = requests.get(A)   # 1 秒，本线程卡死
    b = requests.get(B)   # 1 秒
    c = requests.get(C)   # 1 秒
    # 还是 3 秒
```

GIL 在等 I/O 时确实释放了，**但受益的是别的线程**。卡在 `get(A)` 的这个线程一步都动不了。

> 线程池让「服务能同时处理 40 个请求」，不让「任何一个请求变快」。

### 线程 vs 协程

| | `def` | `async def` |
|---|---|---|
| 谁决定切换 | **操作系统**（抢占式，随时） | **代码自己**（只在 `await`） |
| 阻塞了什么 | 那个线程 | 整个事件循环 |
| 切换成本 | ~1–2 µs，进内核 | ~0.1 µs，用户态 |
| 单个等待单位 | 1 MB(Windows) / 8 MB(Linux) 栈 | 几 KB |
| 并发上限 | 40 | 几万 |

两个都是**并发**（等待时换人干活），都不是**并行**（同时跑字节码）。

> 异步的意义不是「能并发」——线程也能。是「并发单位便宜到能开几万个」。

### 线程池里不能操作异步

三层都不行：

1. **语法**：`await` 只能写在 `async def` 里，同步函数里写直接 `SyntaxError`
2. **技术**：`asyncio.run()` 可以硬开一个新循环，但那个 worker 线程整个被占着，收益为零；而且和主循环隔离（`got Future attached to a different loop`）
3. **设计**：事件循环为了**避免**阻塞，线程池为了**容纳**阻塞。在收容所里搞逃避阻塞，白转一圈

方向是单向的：

```
异步（循环里） ──to_thread──► 同步（线程池）   ✅
同步（线程池） ──asyncio.run──► 异步            ❌ 没收益
```

**一个函数只选边站，不两头下注。**


### 这一段要记的清单

必须知道：

1. 同步库（`requests`、同步 SQLAlchemy）→ 写 `def`，让框架丢线程池

3. `async def` 里塞任何同步阻塞调用 = 整个服务单线程排队
4. 线程池默认 40，这是并发的真实上限
5. 线程池里没有事件循环，`asyncio.get_event_loop()` 直接抛异常

6. 普通函数在哪个线程，看调用者，不看自己怎么写


不用知道：anyio 的线程调度实现、抢占式的内核细节、协程的内存布局。






---

**一句话**：

> `def` / `async def` 不是风格选择，是「这个函数里每一步是不是可暂停的」的声明。
> 同步库就写 `def`，全链路异步才写 `async def`，中间没有第三种。




#  下午：JWT 换数据库版 + CORS

##  JWT 不存的是「会话」，不是「用户」

| 存什么 | 在哪 |
|---|---|
| 用户名、密码哈希、角色 | MySQL `users` 表 |
| 谁现在登录着、token 本身 | 不存，客户端自己拿着 |
| 用户信息的一份快照 | token 的 payload 里 |

payload 里那份用户信息是**复印件**，不是档案室。

登录那一刻查一次库，把结果签进 token；之后每个请求只看 token，不再查库。

所以「数据库版」只改了一行——登录时的取数来源：

```python
# 内存版
for u in USERS:
    if u["username"] == body.username: ...

# 数据库版
user = session.scalar(select(User).where(User.username == body.username))
```

`decode_token` **一行没改**，它从来不查库。


### JWT 的代价：签出去收不回来

payload 里的 `role` 是快照。改了库里的 role，旧 token 里还是旧的，直到过期。

想立刻踢人只能加黑名单或者 `token_version`——那时候 JWT 就真的存库了。

> 短过期时间换来的是「权限不一致的最长持续时间」。

### HTTPBearer 不验签


```python
cred = Depends(HTTPBearer())     # 只做了三件事
```

1. `Authorization` 头在不在
2. 是不是以 `Bearer ` 开头
3. 把后面的字符串原样交给你

**不验签、不查 `exp`。** 真正的校验只有 `decode_token` 做。

结果：`/docs` 上画着锁，`Bearer abc` 却能拿到全部数据。旁证是那 6 个接口都写了 `cred = ...`，函数体里一次都没用过。

```python
def current_user(cred: HTTPAuthorizationCredentials = Depends(bearer)) -> dict:
    return decode_token(cred.credentials)
```

> 认证的责任边界在自己的依赖函数里。「挂了个东西」不等于「验过了」。

### 垃圾 token 会 500，不是 401

```python
h,p,s = token.split(".")      # "abc" → ValueError
```

FastAPI 只把 `HTTPException` 转成响应，别的异常一律 500。

500 的时候前端拦截器不会清 token、不会跳登录页，用户卡死在打不开的状态。

```python
except (ValueError, KeyError):
    raise HTTPException(401,"Token无效")
```

> 401 是「你的凭据不行，去重新登录」，500 是「我坏了」。

### CORS：默认值是陷阱

```python
CORSMiddleware(allow_origins=["http://localhost:5173"])
```

默认 `allow_methods=("GET",)`、`allow_headers=()`、`allow_credentials=False`。

只写 origins 的话：GET 能过，带 `Authorization` 的 POST 预检直接被拒。浏览器拦在发请求**之前**，所以**后端日志一条都没有**。

必写三项：`allow_credentials`、`allow_methods`、`allow_headers`。

另一个：`allow_origins=["*"]` 和 `allow_credentials=True` 同时写，浏览器会静默拒绝。

> 跨域失败先看预检响应头。后端日志空白，恰恰是请求没发出去的证据。

### 配置要启动时炸

```python
SECRET = os.environ["JWT_SECRET"]           # 缺了启动失败，报错里有变量名
SECRET = os.getenv("JWT_SECRET")            # 缺了是 None，第一次登录才炸
SECRET = os.getenv("JWT_SECRET","dev")      # 缺了用一个人人都知道的 secret
```

第三种最危险：把「配置缺失」变成「安全漏洞」，而且无声。

判断标准：**缺了会导致错误 → `os.environ[...]`；缺了有合理的默认 → `os.getenv(..., 默认值)`。** 密码、密钥、数据库地址全属于前者。

### 这一段要记的清单

必须知道：

1. 数据库存用户，JWT 存凭据。token 里能签什么，看登录时能从库里查到什么
2. `HTTPBearer` 只取 header，不验签。验签要自己写依赖
3. `decode_token` 要捕获格式错误，返回 401 而不是 500
4. CORS 三个参数必须显式写，漏了后端日志不会有任何痕迹
5. 密钥用 `os.environ[...]`，缺了在启动时就炸

不用知道：黑名单和 `token_version` 的具体实现、bcrypt 的 cost 因子怎么调、预检结果的缓存时间。

---

**一句话**：

> JWT 省掉的是「每个请求查一次会话表」，代价是「会话发出去就收不回来」。
> 而 `HTTPBearer` 只是把 token 从盒子里拿出来——拆开检查，是另一回事。
