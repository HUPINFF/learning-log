## 一、调用大模型的三步

### ① 建客户端 —— 只做一次

```python
client = OpenAI(
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL"),
)
```

这一步**不联网**，只是把"身份 + 地址"打包成一个对象放着：`api_key` 回答"你是谁"，`base_url` 回答"连哪家"。

后面调一百次模型，都用这同一个 `client`。

### ② 发请求 —— 网络的活全在这

```python
resp = client.chat.completions.create(
    model="deepseek-chat",
    messages=[
        {"role": "user", "content": "用一句话说明什么是 API"},
    ],
)
```

**这一句真把数据发出去了，你等的那几秒就在这。** 传的参数就是你"要什么"：`model` 用哪个模型、`messages` 说什么话、`temperature` 要多稳、`stream` 要不要边生成边给。

### ③ 取内容 —— 从大包裹里刨出你要的那一小坨

```python
resp.choices[0].message.content
```

**`resp` 不是一个字符串，是一个对象。** 拆开看：

```
resp                     ← 整个响应的包裹
 └─ .choices             ← "候选答案列表"
     └─ [0]              ← 拿第一个
         └─ .message     ← 那个答案的消息体
             └─ .content ← 文字内容   ← 你要的就这个
```

**为什么这么绕？每一层都有理由：**

| 那一层 | 为什么存在 |
|---|---|
| `choices` 是**列表** | 因为可以一次要多个答案（`n=3`） |
| `message` 是**对象** | 因为除了 `content` 文字，还可能带 `role`、工具调用等 |

不是设计得啰嗦，是它得兼容所有情况 —— 我只是用了最简单的那一种。

> 类比：**收到一个大纸箱，里面塞满泡沫，你要的东西只有小小一件。**
> `resp` = 纸箱，`.content` = 那件东西。得自己一层层拆开拿。

**这三行，以后会写几百遍。** 变的只有 ② 里那几个参数。

## 二、为什么要把 Key 藏进 `.env`

`.env` 是用来放环境变量的。**API Key 绝对不能泄露出去**，所以 `.gitignore` 里写了 `.env`，不把它提交出去。

### 但"删掉就没事了"是错的

**Key 一旦被提交进 Git，之后删文件也没用 —— 它还在历史记录里。**

别人 clone 你的仓库，`git log` 往回翻，照样能翻出那串 Key。GitHub 上还有专门爬公开仓库找 Key 的机器人，**几分钟内就能捡走**，然后你的额度就被刷了。

**所以正确的做法不是"提交后再删"，而是"从一开始就不让它进去"。**

> 这也是为什么变量名必须叫 `OPENAI_API_KEY` ——
> `openai` 这个库会**自动**去读这个名字。换个名字，代码里就得手动传。
> 顺带一提，`.env` 要放在**项目根目录**，因为 `load_dotenv()` 是从**当前目录往上**搜的。

### `load_dotenv()` 到底干了什么

`.env` 说到底只是**一张便签纸** —— 操作系统不认识它，Python 也不认识。没有任何东西会自动去读。

```
        .env  = 一张便签纸（上面写着 KEY=VALUE）
 load_dotenv() = 把便签上的字誊到墙上
  os.getenv()  = 抬头看墙
```

`load_dotenv()` 就干一件事：**读 `.env`，把里面每一行塞进环境变量。**

然后 `os.getenv()` 才取得出来。**少了这一步，`os.getenv()` 永远返回 `None`** —— 哪怕 `.env` 就在旁边。

> ⚠️ 一个精确说法：它改的是**当前这个 Python 进程**的环境变量，**不是 Windows 的系统环境变量**。
> 脚本一结束就没了。说成"打入系统环境变量"是不准的。

`os.getenv()` 在 Java 里对应的是 `System.getenv()` —— 同一个东西，换了个名字。

## 三、`role`、`temperature`、流式 `stream`

### `role` —— 三种身份

| role | 谁说的话 |
|---|---|
| `system` | **你给模型定的规矩**（人设、约束），每次对话开头定 |
| `user` | **用户说的话** |
| `assistant` | **模型之前说过的话**（多轮对话时把历史塞回去） |

**真正的开关是 `system`。** 同一句话、同一个模型，只改 `system` 两个结果差多少：

| | 输出 |
|---|---|
| 不给 `system` | **400 多字**，还带 emoji 和小标题 —— 它在推销自己 |
| 给一条 `system` | `我是AI助手。` |

那条 `system` 只写了一句：*"你只用五个字回答，一个字都不许多说。"*

> 但它其实回了**六个字**（`AI` 算两个字母）—— 它把 `AI` 当成一个词了。
> **这就是模型的本质：它不是在执行程序，是在照着你的话往下编。尽力遵守，但不保证精确。**

### `temperature` —— 模型的"性格"

可以改变这个值来调整模型的性格：

- **值越大**，输出的变化越多，越天马行空
- **值越小**，模型选中同一个词的概率更大

**但不是"绝对一样"。** 拿两组数对着跑就看得出来：

```
temperature = 0     橘座 橘座 橘座 橘座 橘座     ← 5/5 一样
temperature = 1.5   橘座 橘座 橘座 橘子 大橘     ← 开花了
```

**为什么 `0` 也不保证一样？** 它只意味着"每次挑概率最高的那个词"，但开头差一个词，后面就滚雪球全岔开了。而且远程推理有浮点误差，两个候选词概率挨得近时，也会选岔。

> 还有个细节：`1.5` 那组里「橘座」还是占了 3/5。
> **温度是把概率分布摊平，不是重新掷骰子 —— 最可能的那个，依然是老大。**

**所以解析数据要用 `0`**：同一个岗位解析两次，结果必须尽量一致，不然没法入库。

### 流式 `stream=True`

**为什么要流式？** 因为等一整套回答要十几秒，屏幕上啥都没有，像是卡死了。流式的效果是**第一个字 1 秒内就蹦出来**。

**总时间一样，但"感觉"快了一个数量级。**

在请求里加一个选项就行：

```python
resp = client.chat.completions.create(
    model="deepseek-chat",
    messages=[...],
    stream=True,
)
```

拿内容的方式也变了 —— **是 `delta.content`，不是 `message.content`**：

```python
for chunk in stream:
    print(chunk.choices[0].delta.content or "", end="", flush=True)
```

| | 平时 | 流式 |
|---|---|---|
| 拿内容 | `.message.content` | **`.delta.content`** |
| 拿到的是 | 完整一段话 | **一小片** |

**`message` 是"一整条"，`delta` 是"这一小片的增量"。** 流式下没有 `message` 这个概念，写了就报错。

另外两个小地方：`or ""` 是因为最后一片的 `content` 是 `None`（只带个"结束了"的标志）；`end=""` 让它别换行，`flush=True` 让它立刻吐到屏幕上。

## 四、结构化输出：模型说的话不能信

**这是今晚最重要的一块。**

整个项目的流程是：

```
爬取招聘文本  →  【让模型解析成 JSON】  →  存进数据库  →  筛选/排序
                        ↑
                   就是这一步
```

模型会说话，但程序要的是数据。中间这道坎，就是结构化输出。

### 先改一个心态

> **模型吐出来的东西，是"外部输入"，不是"内部数据"。**

它跟**用户填的表单**、**第三方接口返回的 JSON** 是一类东西 —— **都不可信，都要校验**。

程序里永远不该出现"模型应该会给对，所以我直接取"这种想法。

### 翻车现场

一开始我让模型解析一段招聘文本，只 `system` 里求它"输出 JSON"。结果：

| | |
|---|---|
| ✅ 对上的 | `title` `company` `salary` |
| ❌ **名字对不上** | 它给 `location`，我要 `city`；它给 `requirements`，我要 `skills` |
| ➕ **自己加戏** | `type` `benefits` `target_graduation_year` `urgency` —— 我没要，它觉得有用就给了 |

**关键在于：`json.loads` 一点没拦，全部放行。**

> **`json.loads` 只保证"这是合法 JSON"，它管不了"字段对不对"。**
>
> 程序里写了 `data["city"]`，模型给的是 `data["location"]` ——
> **`json.loads` 通通放行，然后下一行当场 `KeyError` 崩掉。**

**栏在门口的那道关，拦不住里面的错误。**

### 两道防线

| | 干什么 | 定位 |
|---|---|---|
| **第一道：提示词** | 把字段名、类型、缺失怎么办**全写死** | 尽量别出错 |
| **第二道：代码** | 解析完自己查一遍：缺的补、多的裁 | 出了错也扛得住 |

只有第一道不够 —— 上面已经证明，模型照样会自说自话。

**第一道**长这样：把字段名一个一个列进 `system` 里，还要说明找不到怎么办、类型是什么。

**第二道**是这三行：

```python
missing = [k for k in FIELDS if k not in data]
extra = [k for k in data if k not in FIELDS]
return {k: data.get(k) for k in FIELDS}
```

最后那一行，**一行干三件事**：

1. **只遍历我想要的字段** → 多余的（`urgency`、`benefits`）自动被丢
2. **`data.get(k)` 而不是 `data[k]`** → 缺的**不崩**，给 `None`
3. **输出结构永远是这几个 key** → 不管模型给什么，**出去的东西是确定的**

> **进来的不可控，出去的可控。** 这一行就是那道闸门。

### 崩溃其实比静默失败好

| 写法 | 结果 |
|---|---|
| `data["city"]` | **程序崩了**，`KeyError` |
| `data.get("city")` | **不崩，返回 `None`** |

很多人学到 `.get()` 就以为解决了 —— **大错。**

`.get()` 只是让程序别崩，`city` 还是空的。数据**悄悄丢了**，程序继续跑，三个月后才发现数据库里一半记录没城市。

> **崩溃是好事 —— 你立刻知道出事了。**
> **静默失败才可怕 —— 它什么都不说。**

## 今晚踩的坑

- **PowerShell 的 `>` 默认写的是 UTF-16**，不是 UTF-8。`pip freeze > requirements.txt` 导出来的文件直接是乱码。以后要手写，或者在 VSCode 右下角确认编码。
- **`python -m pip` 解决不了"没激活 venv"** —— 那是两个不同的问题。`-m pip` 只保证 pip 和 python 配套，它保证不了 python 本身是哪个。
- **`##` 后面必须有空格**，不然 Markdown 不认它是标题。（这一篇第一版就踩了。）
- **终端里冒出 `>>` 不一定是卡住了** —— 粘贴多行的时候也会出现，命令照样会执行。
