### select 里放几列，决定用哪个终止方法

| `select()` 里放的 | 用 | `j` 是什么 |
|---|---|---|
| `Job`（一个实体） | `session.scalars()` | Job 对象 |
| `Job.edu_required, count()`（多列） | `session.execute()` | `Row` |
| `func.count()`（一个值） | `session.scalar()` | 数字 |

用错了**不报错，只是静默丢列**：`scalar` 只给第一行第一列，`scalars` 只给第一列。

```python
session.scalar(stmt)    # -> "本科"      219 条结果全没了
session.scalars(stmt)   # -> ["本科","硕士","博士","专科"]   计数那列被扔了
session.execute(stmt)   # -> 4 个 Row，两列都在
```

一句话：**`scalar` 只要一个值，`scalars` 只要一列，`execute` 全都要。**


### `.all()`

`session.scalars(stmt)` 返回的是 `ScalarResult`——一个游标句柄，不是 list。

```python
res = session.scalars(stmt)      # ScalarResult
rows = res.all()                 # list[Job]  ← 数据在这
```

`ScalarResult` 上**没有** `len()`、没有 `[0]`、不能切片，只能 `for`。`.all()` 之后才变成普通 list。

规矩：**在 `with Session(engine) as session:` 块里面把数据取干净**。出块后 session 关闭、连接还池，没消费完的结果再迭代就报 `ResourceClosedError`——而且报错位置离真正的原因很远。

| 方法 | 拿到 | 行数不对时 |
|---|---|---|
| `.all()` | 全部，list | — |
| `.first()` | 第一条或 None | **不报错**，静默截断 |
| `.one()` | 恰好一条 | 0 条或多条都抛异常 |
| `.one_or_none()` | 0 或 1 条 | 多于 1 条抛异常 |


### `where(*conds)` 动态拼条件

```python
conds = []
if region:
    conds.append(Job.region_main == region)
if edu:
    conds.append(Job.edu_required == edu)

select(Job).where(*conds)
```

**`Job.region_main == region` 不返回 True/False。** SQLAlchemy 重写了 `__eq__`，`==` 造的是一个 SQL 片段：

```python
>>> print(Job.region_main == "广东省")
jobs.region_main = :region_main_1
```

它不会碰数据库，只是拼了一个 WHERE 的零件。

所以 `conds` 是"零件盒子"，`*` 把它拆成位置参数。`where()` 收到多个条件用 **AND** 连；收到零个直接返回原语句，等于不加 WHERE——不报错。

| 传了什么 | 生成的 WHERE |
|---|---|
| 都没传 | 没有 WHERE 子句 |
| 只 region | `WHERE jobs.region_main = %s` |
| 都传 | `WHERE jobs.region_main = %s AND jobs.edu_required = %s` |

**为什么要先攒 list**：`total` 和这一页数据是两条语句，筛选条件必须一模一样，否则 `total=946` 而 `item` 只有 4 条，前端分页全乱。

注意 `if region:` 对空字符串也成立——`?region=` 传空串按"没传"处理，不会去查 `= ''`。


### N+1 实测

广东省 + 本科，20 行，只来自 **6 家公司**：

| 写法 | SELECT 条数 |
|---|---|
| 不加 `joinedload` | **7** |
| 加 `joinedload` | **1** |

7 = 1（查 jobs）+ 6（查不同公司）。

**N 不是行数，是"去重后的关联对象个数"。** Session 里有身份映射表（identity map），按主键缓存已加载的对象，同一个 `company_id` 第二次遇到直接从内存拿，不再发 SQL。

验证：

```sql
SELECT COUNT(DISTINCT company_id) FROM jobs
WHERE edu_required = '本科' AND region_main = '广东省';
-- -> 6
```

| 情况 | SELECT 条数 |
|---|---|
| 20 行，1 家公司 | 2 |
| 20 行，6 家公司 | 7 ← 实测 |
| 20 行，20 家公司 | 21（最坏情况） |
| 20 行 + `joinedload` | 1 ← 实测 |

最坏情况在真实数据里很常见。**同一个接口换个筛选条件，SQL 条数能从 2 跳到 21**——性能不能靠感觉估。

带 `LIMIT` 时 `joinedload` 会把原查询包成子查询再 join，分页不会被行放大：

```sql
SELECT ... FROM (SELECT ... FROM jobs WHERE ... ORDER BY ... LIMIT 20) AS anon_1
LEFT OUTER JOIN companies ON ...
```

身份映射**只在同一个 Session 内有效**。FastAPI 每个请求一个 Session，所以是请求级缓存——对内存是好事，跨请求不省。

数 SQL 的办法（比 `echo=True` 好数）：

```python
from sqlalchemy import event

counter = {"n": 0}

@event.listens_for(engine, "before_cursor_execute")
def _count(conn, cursor, statement, parameters, context, executemany):
    if statement.lstrip().upper().startswith("SELECT"):
        counter["n"] += 1
```

`create_engine(url, echo=True)` 是把每条 SQL 直接打出来，肉眼可见但费眼。


### yield把普通函数变成了生成器函数
 生成器函数的特点是：调用它不干活，得到一个生成器对象generator object  ，一步步next()才会往下走 ，函数不会因为yield就结束

 我们db.py中为什么把生成的session对话对象通过生成器函数yieldc出去给到外层接口函数，而不是用return呢，因为session在db.py的get_db函数中通过with中创建，退出了with我们session就关闭了，如果用了return来返回seesion，return后函数就实现完毕，结束，创建的局部变量全部销毁，这样我们session就失效了，这样我们接口拿到已关闭的Session，一条查询都查不了；我们用yield出去给接口，我们db.py的get_db函数也不退出，with块也不退出，这样我们session保持连接，接口能连接数据库


### 装饰器 `@`

```python
@deco
def f(): ...
# 等价于
f = deco(f)
```

带参数时多一层：

```python
@deco("参数")
def f(): ...
# 等价于
f = deco("参数")(f)
```

`@app.get("/jobs")`、`@event.listens_for(engine, "...")` 都是同一个机制：**登记一下，把函数原样还你**，函数名、参数、返回值全不变。

只要读懂就行，**不需要自己写**。真需要写是等到有 10 个函数要重复同样三行代码的时候。


### `Depends` 抽 session：Session 变成请求级

5 个接口删掉 `with Session(engine) as session:`，参数里加一行：

```python
@app.get("/jobs")
def list_jobs(
  region: str | None = None,
  cred = Depends(HTTPBearer()),
  session: Session = Depends(get_db),
):
```

`Depends(get_db)` 的含义：**"这个参数不用调用方传，框架你去调 `get_db` 拿。"**

每个请求走一遍完整生命周期：

```
请求进来 → 建 Session → 跑到 yield 停住，交出 session
接口执行 → 用这个 session
接口返回 → 从 yield 继续 → with 退出 → close()
```

所以：**每个请求一个新 session，请求之间不共享**。身份映射也就成了请求级缓存。

| 谁用 | 写法 |
|---|---|
| FastAPI `Depends` | 裸生成器，**不加** `@contextmanager` |
| 自己写 `with get_db()` | **加** `@contextmanager` |

`async def` 不行：同步 SQLAlchemy 会卡住整个事件循环，一个慢查询拖垮所有请求。写 `def`，FastAPI 才会丢进线程池。


### `with` 语句被翻译成了什么

```python
with X as y:
    你的代码
```

等价于：

```python
mgr = X
y = mgr.__enter__()
try:
    你的代码
except:
    mgr.__exit__(异常信息)
    raise
else:
    mgr.__exit__(None, None, None)
```

`__exit__` 在**四种离开方式**下都会执行：

| 怎么离开 | `__exit__` 收到 | 之后 |
|---|---|---|
| 正常走完 | `(None, None, None)` | 继续往下 |
| 抛异常 | `(类型, 对象, traceback)` | **异常继续往外冒**（不吞） |
| `return` | `(None, None, None)` | 函数返回 |
| `break` / `continue` | `(None, None, None)` | 跳出循环 |

两个边界情况：

- **`__enter__` 就炸了 → `__exit__` 不跑**（块没进去，没有"离开"这个动作）
- **`__exit__` 不等于"清理"**，它做什么由作者决定：

| 上下文管理器 | `__exit__` 实际干的事 |
|---|---|
| `open(...)` | `f.close()` |
| `Session(engine)` | `session.close()`（**不 commit**） |
| `engine.begin()` | 正常 `COMMIT`，异常 `ROLLBACK` |

**这是 `POST /jobs` 的坑**：`with Session(engine)` 只 close、不 commit。写操作必须自己 `session.commit()`，忘了就是"接口 200、库里没数据、不报错"。

对比 `with engine.begin() as conn:`——`load_db.py` 用的那个才会自动提交，两者别记混。


### `@contextmanager` 是 FastAPI 的转接头，不是我要写的

`with` 只认 `__enter__` / `__exit__`，生成器没有这两个方法。`@contextmanager` 就是那个翻译器：

```python
@contextmanager
def get_db():
    ...            # → __enter__ 的前半
    yield session  # → __enter__ 的 return
    ...            # → __exit__
```

实现上就两句话：`__enter__` = `next(gen)`，`__exit__` = 再 `next(gen)` 一次（异常时 `gen.throw()`）。

**但 `db.py` 里不要加这个装饰器。** FastAPI 靠 `inspect.isgeneratorfunction()` 认人——"函数体里有没有 `yield`"：

| 写法 | 检查结果 | 后果 |
|---|---|---|
| 裸 `def get_db(): yield` | `True` | 当生成器依赖，自动 enter/exit ✅ |
| 加了 `@contextmanager` | `False` | 当普通依赖，把 `_GeneratorContextManager` 对象当 session 塞进来 ❌ |

后者不报启动错误，只在实际请求时报：

```
AttributeError: '_GeneratorContextManager' object has no attribute 'scalar'
```

**而且 `Session(engine)` 根本没建过**（`__enter__` 没调），错误行却指向接口、不在 `db.py`，很难查。


### `POST /jobs` 接数据库

三处 `JobIn` 和表结构对不上，先拍板：

| 问题 | 解法 |
|---|---|
| `source_job_id` 非空 + 唯一，但手工提交的岗位没有原始 id | 改成可空。MySQL 的 `UNIQUE` 允许多个 `NULL` |
| `JobIn.company` 是字符串，表里存的是 `company_id` 外键 | 先查名字，没有就建（get-or-create） |
| `JobIn.edu` vs 列名 `edu_required` | 字段改名，对齐 |

```sql
ALTER TABLE jobs MODIFY COLUMN source_job_id BIGINT NULL;
```

get-or-create 这段是固定套路：

```python
company = session.scalar(select(Company).where(Company.name == name))
if company is None:
    company = Company(name=name)
    session.add(company)
    session.flush()          # 发 INSERT 拿 id，事务没提交

new_job = Job(company_id=company.company_id, ...)
session.add(new_job)
session.commit()
```

#### `add` / `flush` / `commit` 各干什么

| 调用 | 发 SQL 了吗 | 提交了吗 | 能拿到自增 id 吗 |
|---|---|---|---|
| `session.add(obj)` | ❌ 只登记进待办名单 | ❌ | ❌ `company.company_id` 是 `None` |
| `session.flush()` | ✅ INSERT 发出去了 | ❌ | ✅ |
| `session.commit()` | ✅（内部第一步就是 flush） | ✅ | ✅ |

验证过一次：把 `flush()` 注释掉再 POST →

```
IntegrityError: (1048, "Column 'company_id' cannot be null")
```

因为 id 还是 `None`，插 `jobs` 时撞了 NOT NULL。

**为什么必须 flush，不能拿 commit 代替**：同一个事务里要用这个 id 填 `new_job.company_id`。先 commit，公司就写死了，后面岗位插入失败也撤不回来。

| 做法 | 拿到 id | 还能一起回滚吗 |
|---|---|---|
| `flush()` | ✅ | ✅ |
| `commit()` | ✅ | ❌ |

**顺序固定：flush 拿 id → 拼 `new_job` → 最后一次性 commit。**

三个会自动发生、别被吓到的事：

- `commit()` 内部第一步就是 flush，所以不写 flush 也会插入——只是那时 id 你已经用不上了
- `Session` 默认 `autoflush=True`：执行任何查询前先把待办名单刷一遍，保证查到最新数据
- **`commit()` 之后所有对象过期**，再读属性 SQLAlchemy 会重新 SELECT 一次。所以 commit 后访问 `new_job.job_id` 会多发一条 SQL，正常

```python
# 更 ORM 的写法：不填 company_id，直接填对象，不用 flush
new_job = Job(..., company=company)
```

SQLAlchemy 会自己算出"companies 先插"，并回填外键。


### 这一段要记的清单

必须知道：

1. `yield` 是**暂停**，不是"不结束"；恢复它的是 FastAPI（请求结束时推一下）
2. 每个请求一个新 session，用完就关，请求之间不共享
3. `get_db` 用 `def`，不用 `async def`（同步 SQLAlchemy 卡事件循环）
4. `Depends(get_db)` 不加括号；`get_db` 不加 `@contextmanager`

马上会踩：

5. `with Session(engine)` 不 commit——写操作必须自己 `commit()`
6. `add()` 只登记不发 SQL，要拿自增 id 就必须先 `flush()`

不用知道：`@contextmanager` 怎么写、`__enter__`/`__exit__` 的实现、`gen.throw()` 机制——都属于"读源码能看懂"的层级，不是"写业务要用"的层级。

判断标准：会不会用到 / 用错了会不会静默出错 / 报错看不看得懂。


### 今天踩的坑




**1. `sqlalchemy.events.listens_for` 不存在**

```
AttributeError: module 'sqlalchemy.events' has no attribute 'listens_for'
```

| 模块 | 里面有什么 |
|---|---|
| `sqlalchemy.event`（**单数**） | `listen`、`listens_for`、`remove` —— 注册事件用 |
| `sqlalchemy.events`（复数） | `PoolEvents`、`ConnectionEvents` 等事件类，只在文档里出现 |

正确写法：`from sqlalchemy import event`。

**2. `Depends(get_db())` 多了一对括号**

```
TypeError: <generator object get_db at 0x...> is not a callable object
```

`Depends(X)` 要的是**可调用的东西**，不是它的执行结果：

```python
Depends(get_db)     # ✅ 传函数："到时候你调它"
Depends(get_db())   # ❌ 现在就调了，拿到一个生成器对象
```

关键词 `not a callable object`——拿到的是个"东西"，不是个"能调用的东西"。

`HTTPBearer()` 有括号是因为 `HTTPBearer` 是**类**，要先造实例，而实例实现了 `__call__`，所以可调用。`get_db` 本身就是函数，不用再套。
