## 一、编辑器环境 ≠ 终端环境

在 VSCode 里写 Python,有**两个**环境同时在起作用:

| | 管什么 | 在哪看 |
|---|---|---|
| **编辑器** | 补全、报错红线、调试 | 右下角状态栏 |
| **终端** | 实际执行脚本 | 提示符 |

**两者可以完全不同。**

我机器上有四个环境:

| 环境 | 版本 | 说明 |
|---|---|---|
| `base` | 3.14.7 | conda 默认,终端一开就进这个 |
| `minimind` | 3.10.21 | 编辑器当前指向的 |
| `python.language` | 3.13.7 | 独立安装 |
| `.venv` | 3.13.7 | 基于 `python.language` 建的虚拟环境 |

`base` 里**没有** `openai`,`minimind` 里**有**。

于是在 `probe.py` 里写:

```python
import openai
```

**编辑器不报错**(它用的是 minimind),**终端一跑就崩**:

```
ModuleNotFoundError: No module named 'openai'
```

因为终端在 `base`。

> **结论:同一个文件,编辑器说没事,终端说崩了 —— 说明两边不是同一个环境。**

建议让终端和编辑器指向同一个环境。

## 二、依赖冲突是怎么来的

`pip install` 默认装到**全局环境**里,而且**同名不同版本不做区分**:

```
项目 A 要 requests 1.0  ┐
                       ├─ 都往全局里塞 → 打架
项目 B 要 requests 2.0  ┘
```

装了 A 的,B 就崩;装了 B 的,A 就崩。**只能来回卸载重装。**

### 三个生态的对照

| | 包装在哪 | 依赖清单 | 谁装 | 要激活吗 |
|---|---|---|---|---|
| **Python** | `.venv/` | `requirements.txt` | `pip` | ✅ **要** |
| **Java** | `~/.m2/repository/` | `pom.xml` | `mvn` | ❌ 不要 |
| **前端** | `node_modules/` | `package.json` | `npm` | ❌ 不要 |

**只有 Python 要激活。** 因为 Node 靠"从当前文件往上翻 `node_modules`"找包,Maven 靠构建工具临时算 classpath,而 Python 把"去哪找包"焊死在**解释器**身上 —— 想换一套包,只能换解释器。

所以每个项目都该有自己的 `.venv`。激活之后,`import` 只查项目内的 `.venv\Lib\site-packages`,**不再往全局看**。这样两个项目就算用了**同名但版本不同**的依赖,也不会互相打架。

## 三、venv 怎么建

在项目目录下执行:

```powershell
python -m venv .venv
```

建完**要激活**:

```powershell
.\.venv\Scripts\Activate.ps1
```

**提示符变成 `(.venv)` 才算成功。**

### 用哪个 python 建的,就是哪个版本

```powershell
D:\python.language\python.exe -m venv .venv
```

写成绝对路径才能**指定解释器**。直接敲 `python -m venv .venv` 的话,用的是 PATH 里排第一的那个 —— 我这边是 conda `base`,建出来就是 3.14。

### 查看当前终端用的是哪个解释器

```powershell
python -c "import sys; print(sys.executable)"
```

比 `where.exe python` 可靠 —— 后者只告诉你"PATH 上有哪些",前者告诉你"**现在真的在用哪个**"。

## 四、requirements.txt 是干什么的

**它是依赖清单。**

别人 clone 你的项目后,执行:

```powershell
python -m pip install -r requirements.txt
```

就能一次性装齐全部依赖。**这是实现"换台机器也能跑"的工具。**

### 和前端对照

| | 命令 |
|---|---|
| Python | `pip install -r requirements.txt` |
| 前端 | `npm install`(不用给文件名) |

**但严格来说,`pip install -r requirements.txt` 真正对标的是 `npm ci`。**

- `npm install` → 按 `package.json` 装,版本有一定浮动
- `npm ci` → **严格按 `package-lock.json` 装,一个版本都不许差**

`requirements.txt` 是用 `pip freeze` 生成的,带 `==` 精确版本,**本身就是锁**,所以对标 `npm ci`。

## 五、venv 和 conda 的区别

| | venv | conda |
|---|---|---|
| **隔离范围** | 只有包 | 包 + Python 本身 + 非 Python 库(CUDA/MKL) |
| **能选 Python 版本** | ❌ 母体是啥就是啥 | ✅ 随便选 |
| **包从哪来** | PyPI | Anaconda 仓库 |

我机器上 3.10 / 3.13 / 3.14 **三个版本并存** —— 这是 conda 干的,venv 做不到。

而 `.venv` 是 3.13.7,跟建它的 `python.language` **一模一样** —— 因为 venv 选不了版本。

**conda 存在的唯一理由:** 装 PyTorch 时,背后要一串 CUDA、cuDNN —— 这些**根本不是 Python 包**,pip 管不了。

> job-agent 的依赖全是纯 Python 包,所以**继续用 venv**。conda 等真要装 torch 再学。

## 今天踩的坑

- `python -m venv .` 会把 `Lib\` `Scripts\` 撒进当前目录 —— **末尾的名字必须写全**
- `python -c probe.py` 报 `NameError` —— `-c` 后面**必须放代码**,放文件名会被当成代码解析
- `conda activate` 会**盖掉**正在用的 venv —— 敲命令前先看提示符是不是 `(.venv)`
